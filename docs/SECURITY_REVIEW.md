# Security review before publication

Reviewed on 2026-09-30. The review covers Planroom's application source, REST and MCP adapters, PostgreSQL transactions, HTML preview, dependency tree, container configuration and repository contents. Findings below are implementation findings with contextual severity, not an independent penetration test or a certification.

The repository is private under **eneo-ai/planroom** while the team evaluates it. The code uses MIT with **Sundsvalls kommun and Planroom contributors** as the copyright holder. The original internal planning example is excluded from the distributable source and image; the bundled example is fictional.

## Operational and publication fixes

- Docker's build context uses an allowlist. Configuration, dumps, private keys, test output, Git history and the original internal example stay outside the image.
- Base images and GitHub Actions are pinned to verified digests/SHAs. Dependabot proposes reviewed weekly updates; workflows have read-only repository permissions and no automatic deployment.
- The app runs without root, with a read-only filesystem, dropped capabilities and no new privileges. PostgreSQL has an internal network and no host port. Resource/process limits and log rotation bound runtime growth.
- Startup uses a bounded builder and cleans up only resources created by that invocation. The disposable PostgreSQL runner reports cleanup failures and stops its own child processes on interruption.
- Generated secrets use private file permissions, are never printed, and do not overwrite an existing `.env`. Backup examples protect the last completed dump and do not promote partial files.
- MIT, contribution guidance, private vulnerability reporting, deployment/recovery instructions, API contracts and synthetic example provenance are documented. Municipal ownership and organization links follow Eneo's repository presentation.
- The original planning example is removed from distributable Git history after preserving a private recovery bundle. A bounded scan checks reachable blobs against known credential patterns and configured local secret values without printing their values.

## Policies and migration

Five failed logins within ten minutes lock the email for **ten full minutes from the fifth failure**. That fifth response is 401; later attempts, including a correct password, return 429 until expiry. Successful sign-in clears that email's failures. The global budget can reject legitimate requests during abuse, so shared ingress also needs proxy connection and request limits.

New keys last **90 days**. Existing keys use creation time plus 90 days; keys already older than that receive one migration transition window of 90 days. Migration 001 remains unchanged. The local installation had no personal keys when this migration was prepared.

The legacy password parser supports only the exact previously persisted format. It may be removed when no legacy hashes remain in deployed user tables and operators have an explicit process for upgrading accounts restored from older backups. New accounts and account changes always use the current cost. Unknown users perform dummy verification using the current cost.

Take a protected database backup and retain the previous application image before upgrading. Migration 002 is additive. Prefer leaving its column in place when reverting an application image. Current password hashes require the updated verifier; after a legacy hash has upgraded, recovery must use a version that understands it or restore the corresponding protected backup. Repository-history cleanup has a separate private Git bundle for recovery.

## Boundaries and review outcome

All identified application findings above are addressed in the reviewed source. Actual commands, results and manual checks are recorded in [VALIDATION.md](VALIDATION.md).

Planroom remains a single workspace: all accounts can read all documents. It has no per-document ACLs, SSO/OAuth, account disabling or password-recovery email. Scripts are off by default; explicitly enabled scripts can transmit document data through their own frame navigation. Exported HTML runs outside the preview's restrictions. These are documented product boundaries rather than fixes claimed by this review.

The review does not establish the absence of vulnerabilities, certify accessibility, test a shared reverse proxy or prove recovery in your production environment. A clean npm audit covers that package tree at the time of execution; it does not certify the operating-system packages in an image. Shared deployment still requires correct HTTPS/origin settings and a tested backup and account-lifecycle plan.
